==================================================
21. REDIS / CACHING / RATE LIMITING ARCHITECTURE
==================================================

Redis should be incorporated into the Ascension architecture as a planned infrastructure component.

However, Redis must NOT replace PostgreSQL as the authoritative source of persistent data.

Use the following principle:

POSTGRESQL = SOURCE OF TRUTH
REDIS = CACHE + SHORT-LIVED STATE + RATE LIMITING + FUTURE QUEUE SUPPORT

The goal is to improve performance, concurrency and scalability without creating unnecessary complexity or making Redis a single point of failure.

--------------------------------------------------
21.1 REDIS USE CASES
--------------------------------------------------

Evaluate and implement Redis where it provides clear value, particularly for:

1. Frequently accessed curriculum metadata
2. Frequently accessed level metadata
3. Frequently accessed lesson content
4. Vocabulary data
5. Public/non-user-specific educational content
6. API rate limiting
7. AI request rate limiting
8. Per-user AI usage quotas
9. Short-lived session/state data where appropriate
10. Temporary conversation state
11. Idempotency keys where appropriate
12. Distributed locks where genuinely required
13. Future background job/queue infrastructure

Do NOT automatically cache every database query.

Caching should be based on actual access patterns and performance requirements.

--------------------------------------------------
21.2 CACHE STRATEGY
--------------------------------------------------

Use a cache-aside strategy where appropriate:

1. Application requests data.
2. Check Redis.
3. If cached data exists, return it.
4. If not, retrieve it from PostgreSQL.
5. Store the appropriate result in Redis with a suitable TTL.
6. Return the result.

Frequently accessed but rarely changed data should have longer TTLs.

User-specific and frequently changing data should have shorter TTLs or remain database-driven.

Do NOT cache data where stale values could cause financial, security or educational-progress problems.

In particular, the following should remain authoritative in PostgreSQL:

- User accounts
- Password/authentication records
- Subscription status
- Payment records
- Student progress
- Lesson attempts
- Scores
- Assessment results
- AI usage records that must be permanently tracked
- Administrative changes

Redis may temporarily cache derived versions of these values where safe, but PostgreSQL remains authoritative.

--------------------------------------------------
21.3 CACHE INVALIDATION
--------------------------------------------------

Design explicit cache invalidation for content that administrators can modify.

For example, when an administrator changes:

- Lesson content
- Vocabulary
- Level information
- Curriculum metadata

the relevant Redis cache should be invalidated or refreshed.

Avoid serving outdated educational content indefinitely.

Use predictable cache key naming conventions, for example:

curriculum:{id}
level:{id}
lesson:{id}
vocabulary:{id}
user:{id}:ai_usage
user:{id}:rate_limit

Use versioning/namespacing where appropriate so future schema/content changes do not create stale-cache problems.

--------------------------------------------------
21.4 AI USAGE AND COST CONTROL
--------------------------------------------------

Redis should be considered for fast enforcement of AI usage limits.

Because Ascension subscriptions are intentionally affordable:

General English: approximately $2/month
Professional English: approximately $4/month

AI usage must be tightly controlled.

Design a system that can efficiently enforce:

- Per-user request limits
- Per-user daily/monthly AI limits
- Subscription-specific limits
- Rate limits
- Temporary cooldowns
- Concurrent AI request limits

However, Redis counters must NOT be the only permanent record of AI usage.

Important AI usage and cost information should also be persisted to PostgreSQL for:

- Billing analysis
- Cost tracking
- Auditing
- Usage reporting
- Abuse detection

Redis should provide the fast enforcement layer while PostgreSQL remains the historical source of truth.

--------------------------------------------------
21.5 RATE LIMITING
--------------------------------------------------

Implement or prepare Redis-based rate limiting for:

- Login attempts
- Registration
- Password reset
- Public API endpoints
- AI requests
- Speaking/pronunciation evaluation
- Future voice/conversation endpoints

Rate limits should be configurable through environment/configuration rather than hard-coded.

The architecture should support different limits for:

- Anonymous users
- Free users
- General English subscribers
- Professional English subscribers
- Administrators

--------------------------------------------------
21.6 REDIS FAILURE HANDLING
--------------------------------------------------

Redis must NOT become a single point of failure.

Design the application so that a temporary Redis outage does not unnecessarily make the entire educational platform unavailable.

For non-critical caching:

If Redis is unavailable:

Application → PostgreSQL → response

rather than:

Redis unavailable → entire application fails.

For security-sensitive rate limiting or AI cost-control mechanisms, define an appropriate fail-safe strategy.

For example, if the system cannot reliably enforce an AI usage limit because Redis is unavailable, it should fail closed or use a conservative fallback rather than allowing unlimited expensive AI requests.

Document the chosen behavior.

--------------------------------------------------
21.7 REDIS CONNECTION MANAGEMENT
--------------------------------------------------

Use a proper Redis connection/client management strategy.

Do NOT create a new Redis connection for every request.

Use connection reuse/pooling appropriate to the Redis client and deployment environment.

Configuration must be environment-based.

Do not hard-code:

- Redis URL
- Redis password
- Redis credentials
- TLS configuration

Use environment variables.

Provide the required variables in `.env.example` without exposing real credentials.

--------------------------------------------------
21.8 REDIS MEMORY MANAGEMENT
--------------------------------------------------

Define appropriate TTLs and expiration policies.

Do not allow temporary/cache data to grow without limits.

Consider:

- TTLs
- Maximum memory policies
- Key naming
- Data size
- Serialization format
- Avoiding unnecessarily large objects

Do not store large audio files, videos or other large media directly in Redis.

Use object storage/CDN for media.

--------------------------------------------------
21.9 FUTURE BACKGROUND JOBS
--------------------------------------------------

Evaluate Redis as a possible foundation for future background job/queue processing.

Potential jobs include:

- AI evaluation
- Speech processing
- Audio processing
- Notifications
- Analytics
- Usage aggregation
- Email/SMS notifications
- Content processing

Do NOT introduce a complex distributed job system now unless there is an immediate requirement.

The architecture should remain capable of adding workers later.

--------------------------------------------------
21.10 SCALABILITY
--------------------------------------------------

The Redis architecture must support future horizontal scaling.

The application should NOT depend on in-memory variables inside a single API server instance for shared state.

For example, do NOT rely on:

- In-process session state
- In-memory rate-limit counters
- Local process caches

if that state needs to be shared between multiple backend instances.

Redis should provide a shared short-lived state layer when necessary.

This will allow:

Load Balancer
    ↓
API Server 1
API Server 2
API Server 3
    ↓
Shared Redis
    ↓
PostgreSQL

without inconsistent state between servers.

--------------------------------------------------
21.11 DO NOT OVER-CACHE
--------------------------------------------------

Redis is not a replacement for proper database design.

Before introducing a cache for a particular query:

1. Check whether the PostgreSQL query is already efficient.
2. Ensure appropriate indexes exist.
3. Measure whether caching provides meaningful benefit.
4. Consider the consistency requirements.
5. Define TTL/invalidation behavior.

Do not use Redis to hide inefficient SQL queries.

--------------------------------------------------
21.12 PRODUCTION ARCHITECTURE
--------------------------------------------------

The intended long-term architecture should conceptually be:

Users
   ↓
CDN / Load Balancer
   ↓
Stateless API Servers
   ↓
┌───────────────┬────────────────┐
↓               ↓                ↓
Redis        PostgreSQL      Background Workers
↓               ↓                ↓
Cache /       Source of       AI / Audio /
Rate limits   Truth            Processing
Short state

Static files/audio/video should eventually use appropriate object storage and CDN infrastructure rather than Redis.

--------------------------------------------------
21.13 IMPLEMENTATION RULE
--------------------------------------------------

Before implementing Redis:

1. Inspect the existing backend architecture.
2. Identify the current database access layer.
3. Identify current session/authentication handling.
4. Identify current API rate-limiting mechanisms.
5. Identify existing caching mechanisms.
6. Identify which data is genuinely suitable for caching.
7. Implement Redis using a clean service/abstraction layer.
8. Do not scatter direct Redis calls throughout business logic.
9. Make Redis configuration environment-based.
10. Add graceful failure handling.
11. Test behavior when Redis is unavailable.

Do not rewrite unrelated parts of the application.

--------------------------------------------------
21.14 FINAL REDIS DELIVERABLE
--------------------------------------------------

After implementation, report:

1. Redis technology/client used
2. How Redis is connected
3. Connection management strategy
4. What is cached
5. TTL strategy
6. Cache invalidation strategy
7. Rate-limiting strategy
8. AI quota strategy
9. Redis failure behavior
10. PostgreSQL vs Redis responsibilities
11. Any Redis functionality deliberately deferred
12. How the architecture will scale to multiple API servers

Most importantly:

Redis must improve Ascension's performance and scalability without becoming a single point of failure or creating unnecessary architectural complexity.
